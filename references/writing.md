# 报告归纳与写作

为已选对象写稿、审稿或调整表达时读取。用户格式优先；以下结构和篇幅是默认值，不能为凑条数补事实，也不能为压缩篇幅删除关键状态限定或破坏技术名称。

## 归纳本期贡献

每个已选事项先列出变更、讨论结论、验证、回退及待办，并保留来源 ID、时间或 commit SHA。归纳时回答：整体目标是什么、本期本人推进了什么、当前结论由何证据支持。

- **PR 工作**：先读 Description 理解问题、目标和方案，再用本人区间内的提交信息确定本期进展。commit message 是作者自述；说不清改动或需要核实描述时，按 SHA review 对应 diff。整体成果不等于本期贡献；核对方法与时间边界见 [证据核对](collection.md#pr-description-与本期提交)。
- **会话工作**：调查、评审、答疑和方案取舍都可作为产出；仅保留影响结论的过程。用户请求不等于完成，助手陈述不等于验证；必要时回查配对工具记录。
- **文档工作**：归纳本人本期的新写、修订或评审贡献，不将同事历史正文、阅读材料或计划方案写成已实现成果。保留草稿、待评审等状态。
- **仅有提交**：描述有据的具体变化，不猜动机、收益或合并状态。commit 前缀只帮助理解动作，不决定报告栏目。

同一工作在 PR、提交、会话和文档中出现时合并描述，避免重复报成果。区分“做了什么”和“为什么”，缺少证据的动机、收益和计划省略。

## 组织工作主题

结合共同目标、组件、依赖、时间顺序和会话脉络归并。跨仓库可以是同一主题，同仓库或关键词相同也可能是不同工作；缺乏关联证据时分开写。
同一目标下的功能、修复、重构和回退合并叙述，不先按 `feat`、`fix` 等前缀分栏。

每个主题按“背景/问题（有据才写）→ 方案与调整 → 结果/当前状态”组织，带上关键取舍和待跟进项。
先实现后回退的须说明已回退；原因和最终保留方案有据才写，不把中间尝试写成最终成果。未实施的否决方案仅在解释取舍时纳入。
跨天会话只归纳所选日期内有事件支持的工作，不凭会话跨度补写“继续某事项”。

例如，一次升级包含准入配置、EVM 校验适配和 worker 锁修复时，可在同一主题中说明配套关系；若其中一项无关则单列。
读者应能理解共同目标、各子项关系和最终结果，无需自行拼接提交清单。

## 状态判读

| 证据形态 | 报告表达 |
|---|---|
| 本地 commit，无合并/验证证据 | 已本地提交，其他状态未确认；不写已上线或测试通过。 |
| 只有助手声称完成 | “会话中报告完成，验证状态未确认”。 |
| 工具验证结果 | 按实际命令、退出状态、测试范围及后续事件判断；局部通过不能扩展为全量通过。 |
| PR 合并时间晚于报告区间 | 如需提及，标为后续合并，不倒填成本期状态。 |
| 已提交 Revert | 说明已回退；原因和保留方案未知时省略。 |
| 调查、方案讨论或文档草稿 | 写分析结论、建议或待评审状态，不当作代码实现。 |
| 运行时未提交改动 | 标为当前工作区快照，只写项目名和文件数，不推断积压年龄或历史状态。 |

已验证、已合并、仅本地完成、已回退和等待外部决策分别表达。没有测量数据时不写“性能提升”“稳定性增强”等影响结论。

## 结构与篇幅

主题、项目或工作流作为一级组织单位；“修复、优化、调查、待办”放在主题内部。只有事项彼此独立且按性质更易读时，才用这些类别作一级栏目。
默认用仓库名概括范围，不贴文件路径清单或逐条翻译 commit message。

- 主题用 `##` 标题，名称来自实际证据。主题内内容较长且能概括时可加工作项标题，约 5 句可作长度参考；短事项直接用段落或条目。
- 标题写对象和动作，通常不超过 15 字；准确表达或完整技术名称需要更长时可超过。“背景、现状、回退、最终方案、状态、范围核对”不作为独立通用标题，将这些信息融入叙述。
- 一个工作项通常在 150 字以内，字数按字符计。优先删除无关细节或拆分独立事项；复杂取舍和验证范围可适当展开，不能删掉关键限定。

| 周期 | 默认粒度与篇幅参考 |
|---|---|
| 日报 | 3–6 条，保留模块、变化和必要原因。 |
| 周报 | 3–6 个主题，归并多个子项，不写七天流水账。 |
| 季度 / 年度 | 3–5 个项目或里程碑，每项 2–3 句。 |

周报标题用 `<start> ~ <end> 周报`，季度用 `YYYY年Qn 季度总结`。条数取决于实际工作，不凑数。

## 模板与示例

```markdown
# YYYY-MM-DD 工作日报

## <项目 / 工作主题>

<围绕同一目标的改造、修复和结果合并描述，讲清推进关系。>

## <另一个独立主题>

<做了什么，结果或当前状态。>

## 明日计划

<仅在证据或用户明确给出计划时填写。>
```

没有内容的章节直接省略；用户明确要求计划但没有证据时写“暂无明确计划”。
[日报示例](../examples/2026-10-16.md)与[周报示例](../examples/2026-10-12~2026-10-18.md)仅展示表达方式，项目名和编号均为虚构，不能作为事实来源。

## 审稿与改写

先形成初稿，再以汇报对象的视角通读并实际改写，完成后才交付：

- **重点**：开头是否点明系统、组件或工作流，以及具体解决或推进的问题？删掉“做了很多优化”等空泛概括。
- **关联**：动作与结果是否连贯，配套工作是否合并，独立事项是否分开？避免把文件数、提交数或工具操作当作技术价值。
- **措辞**：标题是否说内容；术语是否准确，内部简称首次出现是否有必要的作用说明？保留必要接口名，删除无助于理解的实现流水账。
- **状态**：写“已验证/已合并”前，在草稿旁记录来源 ID、时间或 SHA；核对验证范围、回退及后续事件，不把暂定方案写成落地结果。
- **密度**：保留架构取舍、兼容性影响、阻塞和有据数字，删除重复背景和无用操作细节；不为字数要求删限定。
- **覆盖**：报告仅包含已选事项，说明影响结论的证据缺口；不泄露敏感信息或评价同事。

例如，“修改了三个文件”应改写成具体行为变化；“相关 3 项测试通过，尚无全量重跑结果”不能缩成“测试通过”。
